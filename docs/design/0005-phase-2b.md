# 0005: Phase 2b choices: live reviewer, variance, policy server, scheduled run

Status: record, Phase 2b, 12 October 2026.

## What actually ran

The first build had no API key in its environment, so it was built and tested against fakes. Later the same day the key was supplied for the live steps, and everything below ran for real on 12 October 2026: a two-post smoke test on Haiku, one pass of 24 posts each on Haiku 5.5 and Sonnet 5.5, five more Haiku passes, and one Managed Agents session on seed story S02. The ledger total is $0.69 over 171 rows. The key was loaded into the environment per command and is not stored anywhere in this repo or its results. The `ant` CLI's stored login (expired) was never used.

The approval in the Managed Agents session was answered by the build agent, under the fictional approver's name and with the post hash, following its instructions. It was not a person's decision, and the README says so.

## Decisions

1. **The ledger is cumulative across runs.** `evals/ledger.py` reads its running total back from `evals/results/spend.jsonl`, so the $50 hard stop covers the whole of Phase 2b, not one process. The stop is a constant: no flag, environment variable or argument raises it (a test checks the source). It checks before every call and after every response, writes the row that crosses the line, then exits with status 3. A `SystemExit` subclass is used so a broad `except Exception` cannot swallow it.
2. **Prices.** Sonnet 5.5 $2 / $10, Haiku 5.5 $0.10 / $0.50, cache reads $0.20 and $0.01, per million tokens, as briefed. The brief gave no cache-write price; the documented 1.25 times input for the five-minute cache is used ($2.50 and $0.125). Haiku 5.5's second card ($0.50 / $2.50 above 100K prompt tokens) is implemented, though no prompt here comes near it. An unpriced model is refused, never guessed.
3. **Prompt shape.** The system prompt is the reviewer skill, a short note on how the review is delivered, the checklist and the brand voice, with one `cache_control` breakpoint on the last block, so every case after the first reads the prefix from cache (about 2,200 tokens, above the 512-token minimum for both models). The user turn is the cited story and then the post, so the post is last. The story comes from `data-pristine/`, with its Status line removed, so the eval does not change as the demo data does. Reading the cited story is what the skill allows (0004, item 3).
4. **Schema.** `messages.parse` with a pydantic model: verdict PASS, FLAG or FAIL; findings as rule id (an enum of the twelve), severity, exact quote and a one-line reason; `what_would_change`; `needs_human`; a short approver summary. Severity goes beyond the brief because H6 and H7 can be either.
5. **Effort.** Sent explicitly at each model's documented default (Haiku 5.5 `medium`, Sonnet 5.5 `high`), so the recorded run says what it ran at. The variance runs use the same defaults. No temperature: non-default sampling parameters are rejected on Haiku 5.5.
6. **Nothing is lost to a bad reply.** A refusal, a `max_tokens` stop or an unparseable reply is recorded as `REFUSED`, `INCOMPLETE` or `UNPARSED`, which scores as a disagreement and a miss, never as a PASS. The installed SDK has no raw-response form of `messages.parse`, and a reply that fails the schema raises inside it with its usage lost, so that case is charged to the ledger at a worst case (the whole prompt uncached and the full `max_tokens` of output) and the row is marked estimated. In the live runs no reply needed it.
7. **Quoted-evidence accuracy** is the share of all findings whose quote really appears in the post, after normalising whitespace and curly quotes but not case. `(no sources block)` counts only when the post has no Sources block. This is separate from the existing "quoted the expected phrase" count.
8. **"Within noise".** Two reviewers on the same 24 cases are compared with an exact McNemar test on the cases only one of them got right. Below p = 0.05 the report calls it a difference; otherwise it says within noise. Each reviewer's agreement also carries a Wilson interval. With 24 cases most differences will be noise, and the report says so.
9. **The live gate uses the stand-in baseline.** It is a floor, so a live reviewer that does worse than the stand-in shows red. `make live` carries on past a red gate (exit 1) and stops on the spend ceiling (exit 3).
10. **`make demo` never calls the API**, even with a key set: step 5 is now a dry run that prints the request plan and an estimate (about $0.03 a pass on Haiku and $0.64 on Sonnet, at a deliberately high guess of 2,500 output tokens a case). The unit tests strip the key before testing live mode.
11. **Stdlib-only, mostly.** The checker, stand-in, harness, variance, labeller tools and demo stay stdlib-only. Live runs need `requirements-live.txt` (pinned `anthropic`, `pydantic`, `pyyaml`); CI installs it so the stubbed live tests run there, and locally those tests skip if it is missing. This narrows 0004 item 15.
12. **The second labeller is pending.** A procedure, a blind export with shuffled neutral ids, a sheet format and Cohen's kappa with a bootstrap interval are in `evals/labels/`. A model was not used in place of a person: agreement with a model would say nothing about whether the labels are right.
13. **The policy server ports the checker to TypeScript.** One process, no Python dependency, and every MCP client gets the same answers. Two implementations can drift, so a parity test runs both over all 24 cases and the five seeded posts and fails on any difference. Python stays the reference.
14. **Deny by default in the server.** Five tools, no resources, no prompts. No tool takes a path; the server reads a fixed allowlist of six files once at start-up and never writes (a test greps the source for write and spawn calls). Every input is a strict zod object, so an extra argument is an error, and text is capped at 20,000 characters. A rule change reaches the server only on restart, after it has passed the approval gate. `check_claim` is an exact match (ignoring case, spacing and a final full stop), never fuzzy: "close enough" is how an unapproved claim gets through.
15. **Managed Agents cannot reach a local stdio server.** Its MCP connections are URLs on the public internet. So the agent declares custom tools with the policy server's five names, and the orchestrator answers each call by forwarding it to the real server over stdio (`scripts/policy_bridge.py`). One policy implementation sits behind every surface. Hosting the server over Streamable HTTP would let the platform call it directly; that is a deployment step, not built.
16. **Two tools beyond the policy.** `get_new_stories` (read-only) is how a scheduled run gets its stories, since every built-in tool, including file reads, is off. `queue_for_approval` is the only write, and it is confirm-first: the orchestrator pauses, shows the draft, and needs a decision and a name. With no decision given and nobody at a terminal the answer is decline. In this phase the queue lives in the run export; a real deployment would write to the approval system.
17. **Networking.** The environment is `limited`, with package managers and MCP hosts off and an explicit host list that is empty, because nothing in the container needs the network. The API accepted the empty list.
18. **Scheduled runs need a responder.** No client is attached when the 07:00 deployment fires, so the session waits at its first custom tool call. The documented production answer is a `session.status_idled` webhook handler; that is not built. `managed_daily.py attach` drives a waiting session, so the first person in can run it. Each fired session carries the $1 budget, and at the cap it pauses rather than fails.
19. **The daily agent runs on Sonnet 5.5** at its default effort. Drafting needs more judgement than reviewing a short post, and a $1 budget leaves room for it.
20. **Agent files are named for `ant apply`.** `agents/harbourlight-daily/agent.md`, `environment.yaml` and `deployment-daily.yaml` follow the one-directory-per-agent layout, so `ant apply agents/harbourlight-daily` would manage them. This build creates them in code instead (`managed_daily.py setup`, which stores ids in `ids.json` and never creates twice). One risk: `agent.md` sits under the plugin's `agents/` folder. The plugin's own subagents are the files directly under `agents/`, and the integrity test checks only those; if a Claude Code version loads nested files as subagents, move the Managed Agents files and keep their relative paths.
21. **Scans skip `node_modules/` and `dist/`.** The deny-list script and the em dash test now ignore installed dependencies and build output, which are not ours to edit.
22. **The orchestrator does not trust the agent's account of its own work** (review finding). Before anything joins the approval queue, the orchestrator runs `check_post` on the post itself and records that verdict; the agent's claimed verdict is kept only as `agent_claimed_verdict`. A FAIL is refused without asking anyone. An approval is bound to the exact text: the approver is shown the post's SHA-256 and must give back at least 12 characters of it, whether at a terminal, in an answer file at the pause, or with a preset `--decision approve --post-sha256 ...`, and a preset covers one queue call only.
23. **Agent-supplied text is inert on screen and in the report** (review finding). Before printing, C0 and C1 control characters other than newline and tab, DEL, and escape sequences are replaced by their repr, so a draft cannot clear the terminal or rewrite what the approver sees. Values in the morning-after report's table escape backslashes, pipes and newlines, so a headline cannot add rows or columns.
24. **Managed Agents spend goes into the same ledger.** The session's platform-priced list cost (tokens plus running time) is recorded as one row and counts against the same $50 stop. The platform reports it rounded to the cent.
25. **The deny-list ignores matches inside opaque API ids.** A random event id in the exported log happened to contain a screened term as a substring. Ids such as `sevt_...` and `sesn_...` are blanked before the second match, so a term is still caught anywhere in prose. A test covers both sides.
26. **The live gate is red, deliberately left so.** Both models raise false positives on the clean posts from the stand-in's 0 to 1, so `baseline.json` (the stand-in's floor) turns red for them. The baseline was not rewritten: whether those H1 findings are false positives is the open labelling question in the README, and moving the floor to suit a model would hide it.
